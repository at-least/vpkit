# Tests

How vpkit is checked: the color themes against their contract and contrast minimums, the variables against VitePress's sources, each component against its proof, the docs theme's layout against VitePress's own rendering, the Rust crate, and the documentation site with its examples and its theme gallery.

```sh
npm install
npm test
```

## Color themes

`test/themes.mjs` holds every theme of `themes/` to the contract, tokens.css's: the 34 `--vp-c-*` colors and the five shadows, in one `:root` block, each color a `light-dark()` pair; and holds every stylesheet of the app kit (tokens, theme, base, prose, the components) to reading nothing but the contract, the docs theme's to the contract and its own `vars.css`. On each side of every theme it checks the contrast minimums of the job each token does: body text 7:1 on the page and on the elevated surface of menus and dialogs, secondary text 4.5:1 on the page, the alternate, soft and elevated surfaces, muted text 3:1, the brand as text 4.5:1 on the page, the elevated surface and a menu item's hover wash, white 3:1 on the three brand fills, the hovered link 4.5:1 as text and dimmed to 0.75 where a container dims it, on the container's tint and on code's tint inside it, and each role's text 4.5:1 on its own tint. The generator must fit every theme to them; a theme it can't fit fails the run. `test/gen-themes.mjs` checks that the generator reads a Helix palette that `inherits` another as Helix does. `node scripts/fit-stock.mjs --check` holds tokens.css's colors to that script's output, VitePress's palette with the same fits. The contrast math the generators fit with is the test's own, `scripts/color.mjs`; the test's CSS reader, `scripts/css.mjs`, reads a value on either side of its pairs.

## Generating themes

The generated themes come from `scripts/gen-themes.mjs`: edit its slot maps, run `node scripts/gen-themes.mjs`, then `node scripts/build-docs.mjs` for the documentation's [gallery](../docs/content/themes.md), then `npm test`. The four hand-tuned ones are edited directly, and the gallery rebuilt the same way. tokens.css's colors come from `node scripts/fit-stock.mjs`, which fits VitePress's `vars.css` by the generator's own steps; `npm test` fails while they are not its output.

## The variables

`test/tokens.mjs` holds `docs-theme/vars.css` to VitePress's `vars.css` and `fonts.css` (the copies in `test/upstream/`): every variable, resolved through its `var()` chain on each side, light and dark, is what it resolves to upstream (the contract names the docs theme aliases VitePress's onto resolve to VitePress's palette; the font families are tokens.css's); the graded containers' colors too; the sidebar's z-index and the hidden navbar's heights in the same scopes; a token's fallback written into a stylesheet is the token's value; and theme.css's five breakpoints are the lengths of upstream's `min-width` media queries, unit included.

`test/utilities.mjs` compiles the semantic names through the Tailwind CLI and holds each to its variable: `text-body`, `text-secondary` and `text-muted`, `bg-page`, `bg-alt`, `bg-soft` and `bg-elv`, the lines, the brand, the gray and the roles with their tints, the shadows, with a variant and an opacity modifier; Tailwind's font sizes beside them; and that the names make no other utility, and the old names (`text-text-1`, `bg-bg`, `text-brand-1`) none.

## Components

`test/components.mjs` runs every `components/<name>/<name>.test.mjs` (and the docs theme's, and `test/page/page.test.mjs`, the page's own rules: the body, a bare placeholder, the focus ring), each case rendered in headless Chromium, both sides on the kit's Inter, light and dark, with `:hover`, `:active` and the other states forced where the case has them, on an emulated touch screen where it must rest, and under Chromium's forced colors where a rule is for them, and compares computed styles by the check's source: `upstream`, with VitePress's original at the tag in `test/upstream/SOURCE`, rendered from its own sources on vpkit's fitted palette written onto VitePress's names, for what is meant to be VitePress's (the colors, the type, the borders, the motion); `reference`, with another rendering of vpkit (a component inside a vp-doc or an alert against itself alone, a touch screen's hover against rest); `golden`, with `golden.json` beside the test, for vpkit's own components and for each named departure from an original (the control height, the pill radius, a flex box, the focus ring), which the check says why. `UPDATE_GOLDEN=1` rewrites the golden files; `CASES='^dialog'` runs the cases it matches. Each product is compiled as it ships, from an entry written from the component directories: the app kit minified, as the apps build it, the docs theme unminified, as vpkit-zola builds it; lengths match within 1/32px. The docs theme's components compile with `docs-theme/vars.css`, VitePress's own palette, and compare with VitePress without the fits.

## Forced colors and motion

`test/forced-colors.mjs` renders, with Chromium's emulation of Windows' contrast themes, the components that show a state only with a background, a shadow or a border color, which those themes replace: a checked and an unchecked toggle, a progress bar at two values, an open and a closed hamburger, a vertical divider against an empty box its size, a badge dot and a dot against an empty box their size, an open drawer against a bare dialog its size, a table's current row against a plain one, a stilled spinner against a full circle its size, and, on the docs theme's stylesheet, a mask icon against an empty box its size, must each render differently. The two sides of a pair must have the same box (a pair whose boxes differ is a failure, not a difference), and the shots wait for every animation to finish, so a pair never differs by motion alone.

`test/motion.mjs` holds base.css's reduced-motion rule to every pseudo-element a stylesheet transitions or animates: the rule's `*` matches elements alone, so a `::before`, `::after` or `::backdrop` that moves must be one the rule names, or it would keep moving under `prefers-reduced-motion`.

## The docs theme's layout

`test/layout.mjs` takes the layout components from pages VitePress rendered (`test/upstream/pages`). The skeleton's components are taken alone: their own elements, child components reduced to their roots. The navbar, the nav screen, the sidebar, the local nav, the aside, the doc footer and the home page are taken as families, each with the components inside it, so rules that cross components count too; there VitePress's side keeps Vue's scoping, each `<style>` compiled by `@vue/compiler-sfc` (the version VitePress locks) with the scope id the page shows. What VitePress renders only in the browser, the outline or the open sidebar, comes from snapshots of vitepress.dev (`test/upstream/pages/hydrated`, taken by `scripts/snapshot-vitepress.mjs`, which refuses a site running another VitePress version). Each case renders VitePress's markup with VitePress's styles and with vpkit's renamed classes, and compares every element's computed style, pseudo-elements and box at widths around each breakpoint, and in dark mode. The markdown is compared whole: the `.vp-doc` of VitePress's markdown guide, without the output of plugins vpkit does not style. The docs theme is compiled unminified here, as a docs theme ships it: Tailwind's `--minify` rounds numbers to six digits, and VitePress's `line-height: 1.3333333` as `1.33333` makes each `h2` 1/64px shorter. `docs-theme/layout.css`, `docs-theme/vars.css` and `prose.css` are written by `scripts/vitepress-port.mjs` from VitePress's sources; `node scripts/vitepress-port.mjs --write` rewrites them after a re-sync, and the tests fail if a file is not its output.

## The Rust crate

`test/rust.mjs` holds `rust/`, every feature on, to `cargo fmt --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test --all-features` and `cargo doc --no-deps --all-features` with warnings as errors, in the crate's own target directory. Each component's test renders its example (`components/<name>/examples/<id>.html`) and compares it with its output; the `css` feature's test checks the embedding holds the kit and writes it out; the examples in the crate's documentation run as tests too; and a public item without documentation fails (`missing_docs`). The documentation it builds, `rust/target/doc`, is what `test/docs.mjs` checks the site's links against.

## The documentation

`test/docs.mjs` builds the documentation site, `docs/`, with [zola](https://www.getzola.org), with vpkit-zola from a sibling checkout (`docs/themes/vpkit-zola` links to `../vpkit-zola`), under a path as GitHub Pages serves it, and renders its pages in headless Chromium, where nothing outside that path answers. Every component directory has a page and every page a directory, and every example file is shown by its page, and every example works: its frame loads its example stylesheet, which styles each class the example's markup uses, follows the page's appearance, and is as tall as its content. The [theme gallery](../docs/content/themes.md) has a card for every theme; the site is on the stock colors from the first frame (the page and the docs theme's frames on docs-theme/vars.css's, VitePress's palette; the app kit's frames on tokens.css's), with the stock card pressed; a pick recolors the page and its example, light and dark, and the next page the session opens from its first frame, and keeps its card pressed on the next visit, a name the URL encodes too; two picks back to back never pass through the stock colors; the stock card takes the page back, even pressed while a pick is still loading, and a pick whose stylesheet no longer exists is forgotten; with JavaScript off the stock colors; no page raises an error; every theme count in the pages and the README is the index's; every component the Rust crate exports is linked from its page, and every link into the crate's documentation, which the test serves under `/rust/` as the docs workflow publishes it, leads to a page it has. `node scripts/build-docs.mjs --check` fails when `docs/examples/` (the copies of the components' examples), `docs/static/example.css` and `example-docs-theme.css` (the frames' stylesheets) or `docs/static/themes.json` (the gallery's index) are not what the sources need; `node scripts/build-docs.mjs` rebuilds them.
