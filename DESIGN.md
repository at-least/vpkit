# The component library: its design

vpkit's components are VitePress's look as CSS classes an application page can use (`vp-btn`, `vp-input`, …). Thirty-eight exist, in thirty-seven files (`vp-label` and `vp-field-error` share `field.css`). This is the design of the library as a whole: what a component is, the rules every one follows, how it is proven, when a new one is built, what stays a utility, the hypertext crate for their markup, and where the apps built on vpkit stand on them. The documentation (`docs/`) documents what ships; this documents what is decided.

What is called measured here was measured against VitePress v2.0.0-alpha.20 (`test/upstream/SOURCE`) and the apps' sources in their sibling checkouts (`../totality`, `../own-drive`, `../crashcart`); a claim marked *guessed* is one nobody measured.

## What a component is

A component is a class, or a block of a few classes, that gives an element the look of one of VitePress's components, and nothing else: no JavaScript, no page layout, no behavior beyond what CSS reads off the element's own state. The app opens the dialog and toggles the switch; the component shows the state the app set.

- Each component is one file, imported on its own (`@import "vpkit/button.css";`), so a site ships only the components it uses. The files are plain CSS in Tailwind's `components` layer, compiled by the site's Tailwind build with everything else.
- Each has a **source**: a VitePress component or stylesheet at the pinned tag, rendered next to the port in headless Chromium and compared property by property (`test/compare.mjs`); or, where VitePress has no such component, a **recipe** taken verbatim from one of the apps built on vpkit (`test/recipes.mjs`, with its path and date), compared the same way.
- The components are the **app** parts of VitePress: a button, a badge, an alert, a card, a table, an input, and the ones in the catalogue. VitePress's docs layout (navbar, sidebar, outline, home page, search box) is `layout.css`, which keeps VitePress's markup and names with BEM separators, and its markdown is `content.css`; `layout.css`'s header has their rules, `test/layout-map.mjs` the map. `base.css` carries VitePress's `body` rule (the page colors, `text-rendering: optimizeLegibility`, the font smoothing, `text-autospace: normal`, `text-spacing-trim: normal`) and `input::placeholder, textarea::placeholder { color: var(--vp-c-text-3) }`, in `@layer base` where upstream has them in `@layer __vitepress_base`, so a utility on the element (`bg-alt` on `<body>`) still wins; `vp-input`'s placeholder is that `text-3`, not totality's recipe color. This document is about the app components.

### Who the library is for

Three applications import vpkit components — **totality**, **own-drive** and **crashcart** — and they are the evidence for what an app needs:

- totality's two sites, its store (`../totality/crates/store`) and its admin (`crates/admin`), import every component they have a use for: `vp-btn`, `vp-input`, `vp-label`, `vp-field-error`, `vp-choice`, `vp-alert`, `vp-badge`, `vp-card`, `vp-table`, `vp-link`, `vp-code`, `vp-spinner`, `vp-toggle`, `vp-icon-btn`, `vp-skip`, `vp-nav-link`, `vp-topbar`, the store's `vp-hamburger`, and `content.css` for both sites' `vp-doc` pages. Their shared recipes are the constants of each site's `src/ui.rs` and, for the two sites' common ones, of `crates/web/src/ui.rs`.
- own-drive (`../own-drive`) imports `vp-btn` with `vp-btn-danger`, `vp-icon-btn`, `vp-dialog`, `vp-toast`, `vp-card-outline`, `vp-progress`, `vp-empty`, `vp-topbar` with `vp-topbar-title`, `vp-toggle` with `vp-toggle-appearance`, `base.css` and `icons.css`; its recipes are the constants of `src/web.rs`.
- crashcart (`../crashcart`) imports them one by one over the dashboard classes that stayed its own (`pager`, `stat-card`, filter chips, stack frames, charts; `src/web/styles/app.css`), and its needs count as an app's.

vpkit-zola imports the layout, the markdown and `badge.css`, and gets `base.css`'s body and placeholder rules through vpkit's `index.css`. own-mail borrows the `--vp-*` names for a design of its own (macOS Mail's) and imports nothing from vpkit, so its recipes are not evidence of what vpkit should hold. Demand in the catalogue is counted over the three apps, by the sites in their sources.

## Rules

Every component follows these.

1. **One component, one file, in `@layer components`.** A utility on the same element always wins (`class="vp-btn px-8"`). Nothing is unlayered; nothing uses `!important` (measured: none in the thirty-seven component files).

2. **Flat names.** The block is `vp-<name>`; a modifier is `vp-<name>-<modifier>`, used only together with the block; a part is `vp-<name>-<part>`. No BEM separators: `vp-btn-brand`, `vp-card-title`, `vp-alert-title`. (`layout.css` is BEM, `vp-content--has-sidebar`, because VitePress names child components after their parents' parts; app components have no such collisions.) A part keeps VitePress's own name where the original has one: VPFeature's `.title` is `vp-card-title`, the custom block's `.custom-block-title` is `vp-alert-title`. A modifier's rule is the compound `.vp-x-mod.vp-x`, modifier first, so it wins over the block whatever the file order, and so tools that look for a class at the start of a selector find it (totality's CSS coverage test).

3. **An app block never takes a layout block's name.** `layout.css` has `vp-button` and `vp-feature` (VPButton and VPFeature as the home page needs them); the app versions are `vp-btn` and `vp-card`, so a page can load both files. The same holds for the toggle and the menu: VPSwitch is `vp-switch` in the layout, so the app's toggle is `vp-toggle`; VPMenu is `vp-menu`, so the app's menu is `vp-dropdown`.

4. **States are attributes, never classes.** `vp-btn:disabled`, `vp-input[aria-invalid="true"]`, `vp-toggle[aria-checked="true"]`, `vp-dropdown-item[aria-current]`. The markup an app already writes for accessibility is the markup the component reads, so there is nothing to keep in sync. (The layout's `vp-sidebar--open` and friends are the classes VitePress's own Vue components toggle, kept as they are.) The element supplies its role and its cursor: `vp-btn` goes on `<a href>` or `<button>`, which bring the pointer (`base.css` gives enabled buttons one). A component sets a cursor only where its original does (the details block's summary) or where the element has none to give (a label drawn as a choice card), plus the additions the apps asked for, the not-allowed cursor of a disabled button and of a choice card whose control is disabled.

5. **Component-local variables.** The block sets its own `--vp-<name>-*` from the theme's tokens (`--vp-btn-bg: var(--vp-button-alt-bg)`); a modifier overrides the locals and nothing else (`.vp-btn-brand.vp-btn { --vp-btn-bg: var(--vp-button-brand-bg); }`). Since every element sets all of its own, a component nested in another keeps its colors (an info alert inside a tip alert, tested). A component with no modifiers still declares its colors as locals (`vp-link`'s), so recoloring one block is one rule on it. An app-wide color fix belongs on the theme token the local reads (`vp-link` in the catalogue shows what a local misses).

6. **Rules for what is inside sit behind `:where()`.** `:where(.vp-alert) a`, `:where(.vp-table) th`: no specificity added, so a component placed inside another keeps its own look — a `vp-btn` link in an alert is not restyled as a link (tested), and a component inside an alert keeps its look only because it says so itself: a dropdown item, a tab and a card set their own text-decoration, and the card its color too, so the alert's link rule underlines none of them; a copy line's value sets its own size, padding, radius and ground, so the alert's rule for inline code gives it no chip. Inside a `vp-doc` (`content.css`) the markdown's rules for a link, a paragraph and a heading, `.vp-doc a` and the like, are in `@layer base`, below the components, so a component's own rules and states win there whatever their specificity, as VitePress's own components win by Vue's scoping attribute, which the port drops. Where the markdown sets something a component's element leaves to the page, the component sets it for that place, `.vp-doc .vp-card-title`, as `badge.css` carries VPBadge's rules for the headings — decision 10, which lists them, each component with a case inside a `vp-doc`, compiled with `content.css` as an app compiles it.

7. **Hover is `@variant hover`,** each in a rule of its own (nested in a rule with declarations, it would stay CSS nesting in an unminified build). Like Tailwind's `hover:` it applies only on a device that can hover; VitePress's hovers also stick to a tapped element on a touch screen. Each component has a touch-screen case: with `:hover` forced it must look as it does at rest.

8. **Size and placement are the page's.** No width, no margin, no position: `vp-input w-full`, `vp-btn w-full`, a dialog placed by `showModal()`. The exceptions are VitePress's own and the documentation names them: `vp-table`'s `margin: 1.25rem 0`, `vp-badge`'s `margin-left: 0.125rem`, `vp-card`'s `height: 100%` (VPFeature's, for a grid of equal boxes); `my-0`, `ml-0`, `h-auto` remove them. So do `vp-label`'s 0.375rem below it and `vp-field-error`'s 0.5rem above it, a field's own spacing, kept from totality's recipes. `vp-dialog` has a width (decision 4) and `margin: auto`, which gives the browser back its centering of a modal dialog rather than placing it. `vp-progress` is `width: 100%`: a track has no content to size it, so in a flex row it was 0px wide; a width utility sets another. `vp-skip` is positioned, fixed at the page's corner, as VPSkipLink is and as a skip link must be. `vp-topbar-row` has VPNavBar's `max-width`, the width VitePress centers a bar's content at; `max-w-none` removes it. `vp-drawer` is fixed at the left edge from the top of the viewport to its bottom, 4rem narrower than the viewport and at most 20rem, VPSidebar's panel as a phone shows it: a drawer that doesn't say where it is isn't one (decision 11); `w-*` and `max-w-none` set another width, `top-*` starts it below a bar.

9. **Tokens: only the theme's, only the contract's.** A component reads the `--vp-*` variables of `tokens.css` and no literal color; vpkit adds no theme token (each of the 223 color themes would have to define it). The one exception is `vp-kbd`, whose original has no token to read: VitePress's half-transparent grays, the same in both modes, copied. It reads only the tokens every color theme must define, the contract `test/themes.mjs` derives, and derives anything else from them: `vp-badge-success` is `--vp-c-success-1` on `--vp-c-success-soft`, the two success tokens the contract has. See [The token contract](#the-token-contract) for how the test enforces it.

10. **VitePress's motion.** Colors transition in 0.25s (0.1s on `:active`, as VPButton), surfaces that follow the appearance in 0.5s (the table rows, the menu). `base.css` neutralizes every transition and animation under `prefers-reduced-motion`, so a component carries no reduced-motion rule of its own, unless its original does: the spinner keeps VitePress's, so it stops on a page without `base.css` too. Its rule names `::backdrop` too, a dialog's scrim, which VitePress's `*` doesn't match (one of rule 12's additions outside the components); `test/motion.mjs` holds the rule to every pseudo-element a root stylesheet transitions or animates.

11. **Dark mode comes through the tokens.** A component has no `.dark` rule unless its original has one (measured: three files have one: `toggle.css`, VPSwitch's, which colors its icon by `.dark` and moves the appearance switch's knob, `drawer.css`, VPSidebar's, which gives the phone's sidebar `--vp-shadow-1` in dark mode, and `icon-btn.css`, whose three-way appearance switch, crashcart's, follows `.dark` when the root carries no `data-appearance`, as the two-way switch does, decision 21).

12. **Additions are allowed, listed and tested.** Where an app needs what the original lacks, the component adds it: `vp-btn` is `inline-flex` with a 0.5rem gap so an icon sits beside its label, and dims when disabled. Every addition is named in the file header and on the component's page of the documentation, and tested against the original with the addition written inline (VPButton with `style="opacity:0.5;cursor:not-allowed"`). Every omission is named too (`vp-card` leaves out the feature icon). There are three additions outside the components. `base.css`'s first: a focused input, textarea or select carries a 2px transparent outline (offset 2px) where VitePress has none — VitePress keeps the browser's ring on a focused button and none on a field, which shows its border — nothing paints on screen, but in forced colors it takes the system's focus color (Chromium's forced colors already paint a focused field's border in that color, so `test/forced-colors.mjs` cannot tell the two apart and the compare case holds the values instead; the ring is for an engine that does not). `base.css`'s second: its reduced-motion rule names `::backdrop`, which VitePress's `*, ::before, ::after` doesn't match, so `vp-drawer`'s scrim stops fading with everything else (rule 10; held by a case under `prefers-reduced-motion` against VitePress's scrim, an element its star covers). And `icons.css`'s: under forced colors, which replace the background color an icon's mask paints with by the page's, an icon paints in the system's text color, held by `test/forced-colors.mjs` (an icon against an empty box its size).

13. **Each component ships complete:** the file with its header comment (the markup, the modifiers, the additions, the omissions), its cases in `test/cases.mjs` (box, colors, every state, touch, nested where it matters) and its page in `docs/content/components/`, with live examples (`test/docs.mjs` fails without one). One commit per component, and one per step of any change to the library, each with its cases green (`npm test`) and its page of the documentation.

## The token contract

`test/themes.mjs` holds every color theme to the tokens vpkit's stylesheets reference: every `var(--vp-c-*)` in the root stylesheets, minus the color ramps and the absolutes. The contract covers every shipped file: `themes.mjs`'s `baseCss()` reads every root stylesheet (the components, `layout.css`, `content.css`, `icons.css` included), with `--vp-c-shadow-3` excepted by name — `layout.css` reads it and nothing defines it anywhere, VitePress's own slip in VPSidebar.vue (`box-shadow: var(--vp-c-shadow-3)`, the phone's open sidebar), carried verbatim by the port, so that shadow never paints upstream either (`drawer.css`, the app port of the same panel, writes no light shadow instead) — so a component can read only what the themes define, and the test says so.

The contract is 39 `--vp-c-*` tokens — the 34 of this base list plus the five roles' `-2`:

```
bg bg-alt bg-elv bg-soft border divider gutter
text-1 text-2 text-3 neutral-inverse sponsor
brand-1 brand-2 brand-3 brand-soft default-1 default-2 default-3 default-soft
tip-1 tip-soft note-1 note-soft important-1 important-soft warning-1 warning-soft
danger-1 danger-soft caution-1 caution-soft success-1 success-soft
```

The five are `tip-2`, `important-2`, `warning-2`, `danger-2` and `caution-2`; `--vp-shadow-1` to `-5` are required too. One more variable is required by name, outside that derivation: `--vp-button-brand-hover-bg`, a hex color that takes white text at 3:1. The five `-2` are in the contract because `alert.css` reads them for its link hover colors and `content.css` reads the same five for the custom blocks' link hovers, so the markdown's link hovers on a theme are held too (vpkit-zola). Stock `tokens.css` derives `tip-2` (and `note-2`) from the themed `brand-2`, but leaves `important-2` on the purple ramp and `warning-2`, `danger-2` and `caution-2` on the yellow and red ones, so where a theme does not define one, the role's hovered link keeps VitePress's stock color (warning's yellow `#946300`) rather than the theme's.

**What a `-2` is.** In a theme `brand-2` and the five roles' `-2`s are a hovered link's color; `default-2` keeps VitePress's job for it, the alt button's hover ground (`--vp-button-alt-hover-bg`). VitePress's `vars.css` describes the step otherwise: "`XXX-2`: The color used mainly for hover state of the button." Its stylesheets use those `-2`s as text, though. `brand-2` is the hovered link of `vp-doc.css`, of the layout and of code in a link (`--vp-code-link-hover-color`); each role's `-2` is the hovered link in its custom block; the one use as a ground is `--vp-button-brand-hover-bg: var(--vp-c-brand-2)` (measured, over vpkit's and VitePress's CSS). In dark mode the two jobs can't share a color: in the dark half of all 222 themes, and in stock VitePress's, no color takes white text at 3:1 and also reads at 4.5:1 as a hovered link dimmed to 0.75 on the info container's gray tint (measured over the sRGB cube in steps of 3; the same search finds such a color in a light half). So a theme keeps `-2` for the text job and gives the brand button its hover ground through `--vp-button-brand-hover-bg`, the variable VitePress already has for it. That is the departure from `vars.css`: a theme's `-2` is fitted as text, and a consumer that paints one as a button's ground no longer gets a ground fitted for white text.

**What the test holds**, in both halves of every theme: body text 7:1 on the page and on the elevated surface (menus, dialogs, toasts); secondary text 4.5:1 on the page, the soft surfaces and the elevated one; muted text 3:1 on the page; `brand-1` 4.5:1 on the page, the elevated surface and a hovered menu item's gray wash; white on `brand-3` and on `--vp-button-brand-hover-bg` 3:1; `brand-2` 4.5:1 as text on the page, the elevated surface and inline code, and dimmed (painted as 0.75 × the color + 0.25 × the ground, as `custom-block.css` and `alert.css` paint a hovered link) on the gray tint and on code inside it; each role's `-1` 4.5:1 on its tint, and its `-2` dimmed on its tint and on code's tint inside it. The 223 themes pass with 19,401 checks, 0 failed.

Stock `tokens.css` is VitePress's verbatim and is not held to them: its dark `brand-2` is 4.14:1 on the page by totality's measurement. `themes/vitepress.css` is the stock palette with its shortfalls fitted, held to the contract like the other 222, written by `scripts/fit-vitepress.mjs` from `tokens.css` (`npm test` checks it is that script's output), and imported after vpkit by every app (totality's store and admin, own-drive, crashcart). Through the contract the stock palette fails 27 checks — every role's `-2` dimmed to 0.75 in its container paints 2.2 to 4.1 in both modes, and dark `brand-2` as text (4.14:1 on the page) and dimmed in the gray containers (3.49:1 in an info block); beyond the contract it also misses the AA numbers the apps had measured, white on light `brand-3` at 4.48:1 and borders under 3:1, so the theme fits: light `brand-3` #5672cd to #5571cb, light `brand-2` #3a5ccc to #23387c with the roles' `-2`s likewise, dark `brand-2` #5c73e7 to #b4bff4 as text with the brand button hovering #3554bc and pressing #2e4aa6, borders #c2c2c4 to #939395 and #3c3f44 to #67696d.

**How the generator meets it** (`scripts/gen-themes.mjs`; the generators are it, `scripts/fit-vitepress.mjs`, `test/gen-themes.mjs` and `scripts/color.mjs`, and `npm test` is node from end to end, `test/themes.mjs` importing its paint, luminance and contrast from `scripts/color.mjs`, so the fits and the checks are one implementation):

- each `-2` is its `-1` moved toward black in light and toward white in dark, interpolated from the `-1` until it passes everywhere it is drawn (`fitAll`), since a rounded 4% step stalls short of black and white (at 12 and 243 per channel);
- `brand-2`'s old value, fitted for white at 3:1, is emitted as `--vp-button-brand-hover-bg`;
- in a dark half whose elevated surface is mid-tone (voxed's olive), `bg-elv` moves toward the page until white reaches 7:1 on it;
- a tint that leaves a hovered link no room, where even black or white dimmed to 0.75 falls short on the tint or on code's tint inside it, is thinned by 0.01 until it has room, never below 0.06; a tint that can't make room by then keeps its alpha, and the test fails the theme;
- in a dark palette, a page too light to leave a hovered link room even at the 0.06 floor (white dimmed to 0.75, on 0.06 of white and on code's tint inside that) moves toward black until it does — it changes one theme: seoul256-dark-soft's page, `#484848`, still lighter than seoul256-dark's `#3a3a3a`;
- a palette's declared background is read under Helix's quoted key (`"ui.background"`) too;
- a palette that `inherits` another is read as Helix merges them (its `merge_themes`): the child's top-level keys replace the parent's whole, and the two palettes merge entry by entry, the child's winning;
- `composite()` is the test's own paint (halves rounded up by `Math.round`);
- Helix's TOML is read by `smol-toml` (1.9.1, a devDependency, since Node has no TOML parser), and the vendored palettes have no integer-like keys, so a plain object keeps their order; the generator runs its loops only as a script, so its test imports it, and `test/gen-themes.mjs`'s eight checks hold the inherits merge, two of them failing against a copy whose merge drops the child's palette entries;
- one CSS reader, `scripts/css.mjs` (the contract test's depth-aware block parser and build-docs's `var()` resolver), serves the fitter, build-docs and the tests.

The four hand-tuned themes (github, catppuccin, nord, rose-pine) carry the same fits (`brand-2`, the `-2`s, and `brand-1` in github's and nord's dark halves) and keep their old `brand-2` as `--vp-button-brand-hover-bg`.

Two kept deviations from upstream in `tokens.css`: the graded containers' palette is literal and on `:root:has(.vp-graded-containers)` (0,2,0), where upstream has `var(--vp-c-orange-*)` and `var(--vp-c-yellow-*)` on `:root:where(:has(…))` (0,1,0), so the opt-in beats a color theme's warning and caution and does not follow a theme that redefines orange or yellow (`tokens.css` says why); and `--vp-font-family-base` names Inter, where upstream names it only in `fonts.css`, so a page that skips `fonts.css` still asks for a locally installed Inter.

**Assumptions** the contract rests on:

- measured: in dark mode one color can't do both jobs (222 of 222 themes, and stock VitePress);
- measured: `brand-2` and the roles' `-2`s are text everywhere in vpkit's and VitePress's stylesheets, except `brand-2` through `--vp-button-brand-hover-bg`;
- measured: of the apps, only own-drive painted a theme's `brand-2` or role `-2` as a ground (`danger-2`, its solid danger button's hover), and it hovers on its own `--od-danger-solid-hover`; totality's brand button is `vp-btn-brand`, whose hover ground is `--vp-button-brand-hover-bg`, on `themes/vitepress.css`;
- guessed: no consumer outside these repositories paints a theme's `brand-2` or role `-2` as a ground.

One consequence for a component: `vp-btn-danger` is the grounded form only (danger text on the danger tint, laid over the page color). A solid one needs grounds for white text, at rest and hovered, and the contract has neither: the themes define no `danger-3`, and a theme's `danger-2` is link text. own-drive derives both per theme with `color-mix()`, its `tests/color_themes.rs` holding white text at 3:1 on the rest and the hover in all 48 of its theme modes.

## How a component is proven

`test/compare.mjs` renders a case twice in headless Chromium, with the original's classes and stylesheet and with vpkit's, in light and dark mode, and compares the computed styles of the elements the case names, with `:hover`, `:active` and `:focus` forced where the component has them, and on an emulated touch screen where it must rest. Lengths match within 1/32px because the shipped build is minified. A difference is a failure unless `known` lists it with its reason, and a `known` entry that stops occurring fails too. Under `CASES=<regex>` only the matching cases run, and only the known entries those cases hit are still required to occur. The upstream stylesheets load in VitePress's order (`custom-block.css` before `vp-doc.css`, as its `without-fonts.ts` imports them), and an original that VitePress renders inside `.vp-doc` (a custom block) is rendered there, since `.vp-doc a` follows `.custom-block a` at the same specificity. `compare.mjs` writes no page colors inline on `<body>`: each side's `base.css` paints the page, and the page cases (the page, a `vp-input` placeholder, a focused field) measure the body and the placeholders against upstream's `base.css`.

Computed styles can't show what forced colors do, because the browser replaces backgrounds and drops shadows when it paints. `test/forced-colors.mjs` renders the components whose state is drawn only with a background under emulated forced colors and requires two states to differ in pixels: a checked and an unchecked toggle, a bar at 40% and at 0%, an open and a closed hamburger, a vertical divider against an empty box its size, a badge dot against an empty box its size.

A clone of vuejs/vitepress checked out at the SOURCE tag (`../vitepress`, clean at v2.0.0-alpha.20) is the standard every ported or copied file is held to, and `test/upstream`'s 63 style and component files are byte-identical to it (`pages/` holds rendered snapshots, not copies). `test/tokens.mjs` (in `npm test` right after the theme test) holds `tokens.css` to upstream's `vars.css` and `fonts.css` (every custom property with the same value), each graded literal to upstream's orange or yellow of its mode, and `theme.css`'s breakpoints to upstream's media queries, with a known list of accepted differences as `compare.mjs` has. Neither `icons.css` nor `fonts.css` is held to the clone by a test (the theme test reads both and finds no token in them); both are checked by hand: `icons.css` is upstream's 22 rules verbatim plus vpkit's two additions, its forced-colors rule and `vpi-monitor` (Lucide's monitor, crashcart's SVG, for the three-way appearance switch, decision 21) (under forced colors an icon paints in the system's text color), and `fonts.css` is 32 `@font-face` blocks over 16 files, equal. Upstream's main has 11 commits in `src/client/theme-default` past the tag and no newer tag (measured 2026-10-12); `SOURCE` re-syncs by plain copy at a tag, and at the next one #5421 (VPButton's height decoupled from its line height) reaches `button.css` and #5437 (native RTL, a new `--vp-direction-multiplier`) the layout port and `tokens.css`.

For a component from a VitePress original:

- the original's file is added to `UPSTREAM` in `compare.mjs` and to the copy list in `test/upstream/SOURCE`; a `.vue` file contributes its `<style>` block. A `<style>` with `:deep()` (VPSwitch, VPSwitchAppearance, VPMenu) must go through `unwrapDeep` from `scripts/vitepress-port.mjs` first, as the layout port does, because a browser drops a selector with `:deep()`.
- the cases cover the box (display, borders, radii, padding, line height, font, geometry), the colors, each state against the original's, each addition against the original with the addition inline, and the touch screen.

For a component from an app recipe:

- the recipe is copied into `test/recipes.mjs` verbatim, with its file and the date, and `test/entry.css` scans that file so its utilities compile into the test stylesheet; the case compares the recipe on one element with the class on another, light and dark, hover and focus.
- a rule the recipe never had (the textarea's padding) is tested as an addition is, against the rule written inline.

### `vp-input` on `<select>` and `<textarea>`

Demand: own-drive styles its two selects (`web.rs:713`, `web.rs:2381`) as its text inputs; that is the pattern, its input recipe being its own look.

There is no `vp-select` or `vp-textarea`: the one class is the box for the three text-like controls. Measured (a probe in headless Chromium on the shipped build, fifteen assertions): `select.vp-input` already renders the input's box exactly — 44px tall, the input border, background, 8px radius, 16px text and 12px side padding — and a screenshot in both modes shows the browser's arrow, dark on light and light on dark. `textarea.vp-input` keeps the box too but is clamped to the input's 44px with no vertical padding, so `input.css` has one element-qualified rule:

```css
textarea.vp-input {
  height: auto;
  min-height: 2.75rem;
  padding-block: 0.5625rem;
}
```

The block padding is 9px because the input's 24px line sits 9px inside its 42px content box, so with 9px a one-row textarea is the input's 44px box and its text lands on the input's pixels (measured: the insides of an input and a one-row textarea holding the same text, 20,160 device pixels, are identical); a three-row textarea is 92px. `rows` and `resize` stay the markup's; the hover, focus, placeholder and `aria-invalid` rules are the class's and so apply to all three.

- Where a select's text sits is the browser's: Chromium sets it 4px further in than an input's, and 1px lower, as it centers the text on a line height of its own (computed `normal` whatever the class sets) — measured; no compensation in `input.css` (decision 8).
- The option list of a `<select>` is the browser's to draw. UNVERIFIED (the headless browser does not render the popup): that it follows `color-scheme`, which `base.css` sets from `.dark`.
- Cases: `select.vp-input` against `input.vp-input` in the same stylesheet (box and colors without the line height, hovered and focused, plain and `aria-invalid="true"`); `textarea.vp-input` against the recipe on a textarea with the rule written inline, as `vp-btn`'s additions are tested, plain and `aria-invalid="true"`; a one-row textarea against the input, for its height; a mutation run (the padding at 0.625rem, a select with 16px of left padding) turns 18 values red.

### Not components

A pattern stays a utility string in the app when it is layout or spacing, when it has no state, pseudo-element or nested rule of its own, or when it belongs to one app's design rather than VitePress's.

From own-drive's recipes these stay where they are: `MUT` and `SZ` (two utilities), its button rows (`BTN_ROW*`, the `ROWBTN` gaps), its table (`TD`, `TH`, `TR`: bottom dividers only, 0.78rem headers, its own look and not VitePress's bordered table) and its links (`DL`: `text-1` to `brand-1`, no underline) — its cards and its empty state are `vp-card-outline`'s and `vp-empty`'s. totality's `FORM_COLUMN`, `FIELD`, `CHOICE_GROUP`, `RESULT`, `NOTE`, `LEDE` and the `ROSTER_*` rows stay utilities; its `H1`, `H2`, `H3` and `LIST_*` are `vp-doc`'s (VitePress's heading scale, which `vp-doc` gives whole). own-mail's chips, verbs and menus are its own design. crashcart's hint dot, search box, stack frames and charts are its own product, not VitePress's (its filter chips, pager and stat cards are `vp-chip`, `vp-pager` and `vp-stat`, decision 21, and its window pills `vp-btn`'s current state, decision 19).

Two patterns two apps drew that VitePress has no original for — an outlined card and an empty state — are `vp-card-outline` and `vp-empty` (decisions 12 and 14); a table of dividers only (own-drive's `TD`/`TH`/`TR`) stays own-drive's, since crashcart's table is `vp-table`'s bordered, banded grid with other cell padding and a sticky header. crashcart's controls are VitePress's sizes (decision 13) and its `btn-ghost` is `vp-btn-ghost`.

**Class-less markup is `vp-doc`.** `<div class="vp-doc">` around markup an app cannot class (totality's FAQ, course introductions from a cache) gives VitePress's headings, paragraphs, links, lists, code, blockquotes, tables and rules exactly; totality's prose and the admin's whole document column are `vp-doc`. That is what `content.css` is. Measured on a minified build: Tailwind's preflight with `index.css` alone is 20,085 bytes (4,842 gzipped); with `content.css` added, 35,597 and 7,369 — the markdown rules cost 2.5 KB gzipped, code-block rules included. There is no `vp-prose` with the text rules alone: the saving is under 2 KB, and it would mean a filtered second output of the port script to keep in step with `content.css`.

VitePress parts that stay in `layout.css` and are not app components: the doc footer's pager, the outline and its marker, the sidebar items, the hero, the site footer, the team members and the sponsors, the flyout (its position is the navbar's), the search box's shell (a search dialog, not a dialog).

## The hypertext crate

`rust/` is the Rust crate `vpkit`: components as [hypertext](https://crates.io/crates/hypertext) components, for an app that renders its pages with hypertext's `rsx!` or `maud!`, as the three apps do (measured in their `Cargo.toml`s: hypertext 0.12, own-drive and crashcart pinning 0.12.1). The stylesheet stays the component: the crate writes the markup its header documents, and the page still imports the stylesheet. One module per stylesheet (`empty.rs` for `empty.css`), and it holds a component only where the markup is more than a class on one element: `vp-btn`, `vp-input` or `vp-badge` on the page's own element, with the attributes the page gives it, is the class string, and so is a component whose parts the page varies, the copy line, whose button is the page's. It ships `Empty` (`vp-empty`), `Pager` (`vp-pager`: a link to each side where there is a page, a disabled `vp-btn` where there is none, and a `label` the `<nav>` landmark takes, so two pagers on a page are two landmarks), `Stat` (`vp-stat`: its value any `Renderable`, `&str` by default, so a figure with a badge beside it is a `Stat` too, written with every field) and `Field` (`vp-label` and `vp-field-error` around the page's control, with `field_error_id`, the error line's id the control's `aria-describedby` names).

What it holds follows from hypertext's component tag, measured on 0.12.1:

- `..` in a tag (`<Empty title="No issues" .. />`, self-closing: without the slash the tag opens a body that the macro gives back only when it meets a closing tag of another name) fills the fields it leaves out from `Default`. A body is passed to a field named `children` as a `Lazy`, which has no `Default`, so a component with a body takes every field written out.
- A literal value goes into its field as it is: `class="mb-0"` fits a `&str` field and fails on an `Option<&str>`.
- A `#[component]` function cannot take a body (the value moves out of `&self`, E0507), and a struct with a `children: R` field and its own `Renderable` impl can (`<Field ...>control</Field>`).

So a component without a body is a `Default` struct of `&str` fields, `""` leaving a part out, with `class` for the page's utilities on its root (a tag that writes every field leaves the `..` out: clippy's `needless_update` refuses it); a component with a body has only fields the page holds anyway, `Option` for a part that may be absent. A field whose absence would draw a wrong box silently, `Empty`'s title, `Pager`'s three labels, `Stat`'s title and value, panics when empty, each assert naming its field. A field of a generic type (`Stat`'s value) cannot be left to `..`: a tag without it does not compile, since the default type parameter does not drive inference.

The crate writes vpkit's classes and nothing else, never a utility: Tailwind would have to scan a cargo checkout to find one (`@source` on a path that changes with each pin), and rule 8 leaves size and placement to the page, which writes them in its own source. States stay attributes (rule 4): the crate writes the ones on its own elements, and the page the ones on its control (`aria-invalid`, `aria-describedby`). Each component's test renders the markup of its stylesheet's header and asserts the output equal to that header's example, read from the stylesheet itself, so the header and the crate cannot part; `cargo test` in `rust/` runs them and the examples in the crate's documentation, beside `npm test`, with `cargo fmt --check` and `cargo clippy --all-targets -- -D warnings` clean. An app takes the crate from the repository at the commit its stylesheet pin names, `vpkit = { git = "https://github.com/at-least/vpkit", rev = "<sha>" }`, so the markup and the CSS move together.

## The documentation site

The site links its color theme statically: a `<link rel="stylesheet" data-theme="vitepress">` for `themes/vitepress.css` in every page's head through the zola head setting (`docs/config.toml`), with `docs/static/theme-pick.js` right after it, so the theme is there with JavaScript off and fetched beside the page's stylesheet. `theme-pick.js` replaces that link with the session's pick (`sessionStorage`), written with `document.write` as the parser reads the head, so the page's first paint is already in the pick; the stock card's pick is the empty name, which links no theme (the stock colors are `tokens.css`'s own); only the URL is encoded (`penumbra+` is a theme); a pick whose stylesheet no longer exists is forgotten by a capturing `error` listener on the document, and the static link takes the dead one's place. The script spells nothing of its own — the link it removes says the site's theme, its name and URL, so changing the site's theme is a `config.toml` edit.

`docs/static/example.js`, parsed in each example frame's head, writes the page's theme links into the frame so it waits for them before its first paint, and when the page's links change (a pick, the stock card) it swaps them without a gap: the new copies go in first and the old are removed once loaded (a `Promise.all` over the copies), so a frame never shows the stock colors in between. The theme gallery's pick (`docs/static/theme-gallery.js`) records the links the page has and removes them once its own stylesheet has loaded, at once for the stock card; a later pick's link is never among an earlier pick's, so an earlier pick's late load cannot take it.

`test/docs.mjs` holds the site: a page for each component file the component tests compile (`vp-label` and `vp-field-error` share one); every example frame loads `example.css` and styles every class its markup uses, is as tall as its content and no wider than the page at a phone's width, and takes the page's appearance when the switch changes it; the gallery index (`docs/static/themes.json`) is the stock colors then every theme of `themes/`; the site is on the vitepress theme from each page's and frame's first frame until a session picks one; a pick recolors the page and its frames in both modes and the next pages from their first frame; two picks back to back never pass through the stock colors; the stock card pressed while a pick loads leaves no theme linked; a dead pick is forgotten for the site's theme; with JavaScript off the static link alone; and the theme counts the prose states against the index.
